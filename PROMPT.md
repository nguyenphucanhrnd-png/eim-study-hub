## 1. NON-NEGOTIABLE RULES

1. **Single source of truth = `KNOWLEDGE_BASE.md`.** Every theory statement, question and explanation must trace back to a section in that file. The PDFs in `source-pdfs/` are used to **cross-check** (especially diagrams). If the KB and a PDF conflict, **stop and report to me**; do not decide on your own.
2. **Zero hallucination.** If a fact is not in the KB and is not on the `[EXT]` list in the KB, **do not write a question about it**. Do not invent numbers, years, article numbers or definitions.
3. **Follow the ERRATA (KB §9) strictly:** points marked (N) must never be the basis of a correct answer; points marked (T) must carry the extension note in the explanation.
4. **Every MCQ has exactly 1 unambiguous correct answer.** Do not use "All of the above" / "None of the above" / "Both A and B" except in rare cases (≤3% of the bank, with `lockOrder: true`).
5. **Language:**
   - **Question stems, options and case scenarios: English** (matching the exam language).
   - **Explanations, rubrics and website UI: Vietnamese**, keeping English technical terms in parentheses the first time they appear (e.g., "thế quyền (subrogation)").
6. **Never build everything in one go.** Work through the phases in §9; at each **CHECKPOINT** stop, summarize, and wait for my confirmation.
7. Code: TypeScript strict, no `any`, short comments on complex logic, no dead code.

## 3. INFORMATION ARCHITECTURE & FEATURES

### 3.1 Dashboard (`/`)
- Progress per chapter (% of questions done, accuracy %), score history of mock exams.
- **"Chủ đề yếu"**: top 5 topics with the lowest accuracy (minimum 5 attempts) → link to practice that topic.
- Quick buttons: Continue studying · Random practice · Take a mock exam · Review wrong answers.

### 3.2 Theory review (`/learn/:chapterId`)
Each chapter page has this structure:
1. **Key takeaways** (5–8 bullets) at the top.
2. Theory sections rendered from `content/theory/cXX.md` (faithful to the KB, rewritten in Vietnamese with EN terms; tables kept intact).
3. **"Bẫy thường gặp" (common traps) box** for each chapter (e.g., "CIF Hamburg ≠ risk transfers at Hamburg").
4. Interactive tools embedded where relevant (see §3.7).
5. **Mini-check** at the end of the chapter: 5 random questions from that chapter with instant feedback.
6. Left table of contents (sticky on desktop, drawer on mobile); "Đánh dấu đã học" (mark as learned) button for each section.

### 3.3 MCQ practice (`/practice`)
- Filters: chapter (multi-select), topic, difficulty (1–3), number of questions (10/20/30), "only questions not done yet" / "only questions answered wrong".
- **Instant-feedback mode:** after choosing an answer, immediately show correct/incorrect + the full explanation (§5.3).
- Keyboard shortcuts: `A–D` or `1–4` to choose, `Enter` for next question, `F` to flag.

### 3.4 Mock exams (`/exams`, `/exams/:examId`)
- **12 fixed exams × 50 questions**, built per the blueprint in §6; each question belongs to exactly one fixed exam.
- Plus a **"Đề ngẫu nhiên" (random exam) mode**: draws 50 questions from the whole bank following the blueprint.
- During the exam: **60-minute** countdown (configurable), question navigator grid (answered / unanswered / flagged), no explanations shown, submit confirmation if questions remain unanswered, autosave so a page reload doesn't lose progress.
- Results page: total score (/10 and %), time taken, **breakdown by chapter (bar chart)** and by difficulty, list of questions answered wrong → review mode with full explanations. Save history (best score, attempts).

### 3.5 Case studies (`/cases`, `/cases/:caseId`)
- List of cases filterable by chapter and difficulty, with estimated time.
- Case page: scenario (EN) → sub-tasks with a textarea for each task (draft autosaved) → **"Nộp & xem đáp án" (submit & see answer)** button → shows the **model answer (EN)** + **rubric (VI)** as a checklist the student ticks to self-grade → total score saved to history.
- Show "Lỗi thường gặp" (common mistakes) and sources.

### 3.6 Review (`/review`)
- **Wrong-answer bank:** every question answered wrong goes here automatically; a question leaves the bank once answered correctly **2 consecutive times** (simple spaced repetition).
- Flagged questions.
- **Flashcards** (`/flashcards`): glossary terms EN↔VI + key concepts; card flip, "Đã thuộc / Chưa thuộc" (known / not yet known).
- **Glossary** (`/glossary`): instant search, EN–VI.

### 3.7 Interactive tools (`/tools`, also embedded in chapters)
1. **Incoterms® 2020 Explorer (C3)**: pick 1 of the 11 rules → horizontal chain diagram *Seller premises → Pre-carriage → Export clearance → Port/place of loading (on board / first carrier) → Main carriage → Port/place of destination → Unloading → Import clearance → Buyer premises*; three colored bars **COSTS / RISKS / INSURANCE** show who bears what (seller = blue, buyer = amber). Includes the obligation table (licences, carriage, insurance, delivery point). **"So sánh 2 rule" (compare 2 rules) mode** placed side by side. Data is taken 100% from the KB §3.8 table.
2. **ICC Coverage Checker (C4)**: pick a peril → shows AR/WA/FPA/ICC-A/B/C coverage per Table 6.2; rows with ERRATA E-04 carry a footnote.
3. **Payment Flow Stepper (C5)**: step-by-step animated flows for T/T advance, T/T deferred, D/P, D/A (7 steps, Fig. 11.2), L/C (9 steps). Each step has a short description. Includes a **risk comparison for exporter vs importer** across methods (mark `[EXT]`, source: Trade Finance Guide).
4. **L/C Date Checker (C5)**: input issue date, latest shipment date, actual shipment date, presentation date, expiry date, (optional) presentation period stated in the L/C → flag each rule (issue < shipment; shipment ≤ latest shipment; shipment < expiry; presentation ≤ shipment + N days (default 21); presentation ≤ expiry). Write unit tests for every case.
5. **FX & Export Profit Calculator (C2)**: input quantity, price, foreign currency, rate at contract, rate at payment, costs → revenue, gain/loss from FX, gross profit, margin. Preload the slide example (EUR 50,000; 30,000 → 28,000/32,000).
6. **Contract Clause Doctor (C6)** *(optional, Phase 5)*: show a contract clause containing an error → the student picks the error type from a list → feedback.

### 5.2 MCQ
```ts
type OptionId = "a" | "b" | "c" | "d";
interface MCQ {
  id: string;                 // "C5-lc-dates-007"
  chapter: "C1"|"C2"|"C3"|"C4"|"C5"|"C6"|"C7"|"C8";
  topic: string;              // from the §5.1 list
  difficulty: 1 | 2 | 3;      // 1 = recall, 2 = understand/apply, 3 = scenario/analyze
  cognitive: "remember" | "understand" | "apply" | "analyze";
  stem: string;               // English
  options: { id: OptionId; text: string }[];  // exactly 4
  correct: OptionId;
  lockOrder?: boolean;        // true if options must not be shuffled
  explanation: {
    summary: string;          // VI, 1–2 sentence conclusion
    whyCorrect: string;       // VI, ≥ 2 sentences, explains the WHY
    whyWrong: Partial<Record<OptionId, string>>; // VI, one entry for EACH of the 3 distractors
    source: string;           // "KB §5.4 – Documentary Collection: D/P vs D/A"
    extNote?: string;         // "[EXT] UCP 600 Art. 14(c): …" — only from the KB's EXT list
    trap?: string;            // the common trap (if any)
  };
  tags: string[];             // e.g., ["errata-E06", "calculation"]
}
```

## 6. QUESTION BANK & EXAM BLUEPRINT

### 6.1 Blueprint per exam (50 questions)
| Chapter | Questions/exam | Bank total (×12) |
|---|---|---|
| C1 Overview | 3 | 36 |
| C2 Planning | 4 | 48 |
| C3 Pricing (approaches + objectives) | 3 | 36 |
| C3 Incoterms | 12 | 144 |
| C4 Insurance | 6 | 72 |
| C5 Payment | 10 | 120 |
| C6 Contract | 5 | 60 |
| C7 Documents | 5 | 60 |
| C8 Procedures | 2 | 24 |
| **Total** | **50** | **600** |

- Difficulty mix per exam: **20 easy (1) – 20 medium (2) – 10 hard (3)**. The bank for each chapter should keep roughly the same 40/40/20 ratio.
- Within each chapter, spread across topics; no topic may take more than 30% of a chapter's questions in a single exam.
- Keep the number of exams in `config` (`EXAM_COUNT = 12`) so it can be changed to 10 or 15.

### 6.2 MCQ quality standards
- **Question types to mix:** definition/concept; comparison (A vs B); **short scenario** ("A Vietnamese exporter sells … under CFR Osaka. The vessel sinks after loading at Cat Lai. Who bears the loss?"); classification (which one belongs to group…); sequencing of process steps; **calculation** (FX, revenue, gross margin, quantity tolerance, insured amount 110% — only with data in the KB); error spotting (contract clause/document against the L/C).
- Hard (level-3) questions must require **combining ≥2 concepts** (e.g., Incoterms + insurance; L/C + B/L type; contract + documents).
- **Plausible distractors**: built from typical misconceptions (confusing risk point and cost point in C-group rules; D/P vs D/A; FAS vs FOB; clean vs on-board B/L; insurable interest vs subrogation; pro forma vs commercial invoice; CIF=ICC(C) vs CIP=ICC(A)…). Distractors must be similar in length and grammatical form to the correct answer.
- Avoid double negatives. If you must use NOT/EXCEPT → write it in **CAPS** and keep it to ≤10% of the bank.
- Do not let two questions in the same exam give away each other's answers.
- **Calculation questions:** compute and verify with code in `scripts/validate-bank.ts` (store the inputs in `tags` or a `calc` field so they can be re-checked).
- After generation, `build-exams.ts` shuffles option order (seeded, except `lockOrder`) so that **each letter A/B/C/D is correct about 25% of the time (allowed range 20–30%) in each exam**.

### 6.3 Explanation standards
- `whyCorrect` explains **the mechanism/reason**, not just a restatement of the answer. Example: "Under CFR, risk passes once the goods are on board the vessel at the port of shipment (Cat Lai), even though the seller pays freight to Osaka → the loss at sea falls on the buyer."
- `whyWrong` for **each** distractor: state precisely why it is wrong or what it confuses.
- `source` points to the exact KB section. `extNote` only uses `[EXT]` content already present in the KB.
- Length: summary ≤ 40 words; whyCorrect 40–120 words; each whyWrong 15–50 words.

## 8. SCRIPTS & QUALITY CHECKS

`npm run validate:bank` (`scripts/validate-bank.ts`) must check and **fail the build** if:
- JSON fails the Zod schema; duplicate `id`; `correct` not among the options; topic not in the list.
- Missing a `whyWrong` for any distractor; empty `source`.
- Stem duplicates/near-duplicates (normalize + token Jaccard similarity > 0.8 → warning list).
- Count per chapter/difficulty does not match the blueprint.
- A question tagged with an (N) ERRATA item (KB §9) is a correct-answer basis → error.
- A calculation question with a wrong result.

`npm run build:exams`: partition the bank into 12 exams per the blueprint (seeded, reproducible), with no overlap, balanced A–D.
`npm run report:bank`: print a summary table (chapter × difficulty × topic, A–D distribution per exam).

Unit tests: scoring, exam timer/autosave, L/C Date Checker, FX calculator, wrong-answer bank logic (removed after 2 consecutive correct answers).
